## Architecture

```text
ISO client
  → binary TCP framing / HTTP JSON
  → ISO parser and router
  → PostgreSQL card + merchant normalization
  → deterministic txId and action-level idempotency
  → gas preflight
  → relayer submission
  → two-confirmation receipt
  → decoded settlement event
  → ISO response

Evidence:
  iso_messages → chain_operations → onchain_events → contract state/accounting
```

The aggregate `payment_log` remains a current-state read model. Evidence that
must not be overwritten is stored separately in the three append-only tables.
The UI payment API serializes this read model to a stable camel-case DTO.

## Scenario Matrix

The runner writes one JSON artifact per scenario and a combined run artifact.
These rows are executable specifications; received values are populated by the
controlled run.

| Scenario | ISO sequence | Expected RC | Final accounting invariant |
|---|---|---:|---|
| `happy-path` | `0100` → `0200` | `00`, `00` | Available and custody decrease once; locked returns to baseline; merchant increases exactly once |
| `insufficient-funds` | `0100` | `51` | No balance, custody or hold change |
| `duplicate-authorize` | same `0100` twice | `00`, `94` | Funds locked exactly once |
| `duplicate-capture` | `0100`, same `0200` twice | `00`, `00`, `94` | Merchant paid exactly once; no locked remainder |
| `expired-hold` | `0100`, delayed `0200`, `expire` | `00`, `54` | Hold becomes expired and user balances return to baseline |
| `invalid-merchant` | `0100` with unknown merchant | `03` | No accounting change |

## Accounting and Reconciliation

Reconciliation covers four planes:

1. Every actionable ISO request has an operation, and every confirmed
   middleware operation has its originating ISO request.
2. Every confirmed operation has the expected onchain event, and every
   settlement event in the selected block range has a recorded operation.
3. Event history and `getHold(txId)` agree on status, amount, token, user and
   merchant.
4. ERC-20 custody is at least the sum of known available and locked
   liabilities for configured test users.

The live result is written to `backend/data/reconciliation-<timestamp>.json`
and persisted in `reconciliation_run`. The demo exits non-zero if any scenario
or reconciliation plane fails.

## Latency

The middleware records the following phases with bounded raw samples and
percentile summaries:

| Phase | Start/end |
|---|---|
| `parse` | Intake start to validated ISO fields |
| `db_lookup` | Mapping lookup and normalization |
| `gas_estimate` | RPC estimate request |
| `tx_submit` | Signed transaction RPC submission |
| `tx_confirm` | Submission acknowledgement to confirmed receipt |
| `total_iso` | Intake start to final ISO response |

No fabricated latency numbers are included here. The controlled execution
writes `backend/data/m3-metrics-<timestamp>.json`, and the report generator
replaces this section with measured p50, p95, p99, average, minimum and maximum
values.

The local Foundry snapshot is stored in `contracts/.gas-snapshot`. Representative
full-lifecycle test calls currently measure approximately:

| Operation | Local test gas |
|---|---:|
| Authorize | 230,222 |
| Capture | 241,969 |

These are EVM test measurements, not Arbitrum transaction prices. During the
controlled run, every confirmed operation stores `estimated_gas`, `gas_used`,
`effective_gas_price`, `fee_wei`, and timing fields. The generated gas report
aggregates authorize/capture minimum, maximum, average and total fee using the
actual receipt formula `gasUsed × effectiveGasPrice`.

## Security Results

- Role checks cover relayer, token administrator, pauser and default admin.
- Reentrancy protection and malicious callback tests pass.
- Deterministic txIds, terminal holds and action-level operation records prevent
  replay and duplicate settlement.
- UUPS upgrades are admin-only and preserve roles, balances, locked funds and
  holds in the V1-to-V2 test.
- Solvency invariants and fee-on-transfer rejection pass.
- Pause/unpause and permissionless post-deadline expiry are tested.
- Slither: one intentional medium strict-equality finding, four low timestamp
  findings and four informational findings; see `SECURITY_REVIEW_M3.md`.

The browser dashboard and deterministic wallets remain testnet-only. Any
historical test key must be considered public. Mapping administration must be
protected by a gateway or private network in staging; production requires
dedicated authentication and authorization.

## Reproducible Demo

```bash
cp backend/.env.example backend/.env
# Inject a testnet RELAYER_PRIVATE_KEY with RELAYER_ROLE.
./start.sh

cd backend
npm run m3:demo
```

`m3:demo` verifies backend health, executes all six scenarios over TCP, captures
latency and receipt-cost artifacts, runs reconciliation from the starting
block, regenerates this report and exits non-zero on drift.

## Limitations and Next Phase

- The current assets and deterministic accounts are testnet-only.
- Live M3 results depend on externally managed PostgreSQL, RPC and relayer
  credentials and therefore are not committed.
- Synchronous confirmation increases POS response latency; the next phase
  should evaluate asynchronous advice/status messaging.
- Production requires authenticated admin routes, PAN/token log minimization,
  user authorization or spending mandates, velocity limits, refunds, partial
  capture, KYC/AML controls and an indexed complete-liability ledger.
- CI now runs contract, backend, UI and Slither checks; staging should also
  archive demo artifacts and enforce a zero-reconciliation-drift release gate.
